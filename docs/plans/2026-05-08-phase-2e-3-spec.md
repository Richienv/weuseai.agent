## Why this exists

Five gaps surfaced during the Phase 2E-2 build + smoke test that can't ship to a paying customer base:

1. **Bundles never reach the VPS at provision time.** `customer-flow.ts` doesn't pass `bundleTarBase64` to `buildSetupScript()` (deferred from 2E-2). Provisioned customers today get the Phase 2A baseline only — no per-agent bundle.
2. **Invoice handler returns HTML, not PDF.** Production invoices need PDFs. The current Phase 2E-1 `invoice-generator-handler` renders HTML and returns a signed URL; customer pastes that into a browser and Ctrl-P. Acceptable for founder + first 1-2 concierge customers, not for scale.
3. **Tier upgrades require manual SSH.** A customer who pays for a Pro upgrade needs the founder to SSH into their VPS, edit `.env`, `systemctl restart hermes-gateway`. The 2E-2 runbook documents this as Phase 3+ work — but with paying customers imminent, "instant tier upgrade after Xendit webhook fires" is now the table-stakes UX.
4. **Default LLM is expensive.** Current `setup-script.ts` defaults to `claude-opus-4.6` for the BYOK fallback. Per founder validation 2026-05-08: DeepSeek v4-pro is the price-to-value winner across all tiers (~$0.27/M output vs Sonnet ~$15/M). Single global default simplifies the config.
5. **Telemetry table grows unbounded.** `bundle_pull_attempts` is append-only with no retention policy. At ~1 row/customer/boot, scales linearly with customer count × restart frequency.

Plus two cross-cutting items:

6. **JWT-role auth pattern needs to lock across all 9 Edge Functions.** The pattern was discovered + applied to `bundle-publish` during 2E-2. Other admin endpoints (`workflow-execute`, `xendit-webhook`, etc.) still use the old `token === SERVICE_KEY` check, which silently fails the moment Supabase migrates a project to the new `sb_secret_*` key system. We caught it once via 4 live VPS attempts; we can't catch it 8 more times.
7. **Floating IP leak detection has no notification.** `cleanup-orphan-vms.ts --include-ips` was shipped in 2E-2 as detection-only; founder still needs to manually run it + click through dashboard. Without a daily cron + Telegram nudge, the leak just slowly accrues again (~Rp 40k/IP/month silent).

## Architecture

### Tier-bump flow (the new top-priority Edge Function)

```
Xendit dashboard ───► invoice.paid webhook (existing /xendit-webhook Edge Function)
                       │
                       │  body has metadata.tier_upgrade=true,
                       │  metadata.target_tier=pro|studio,
                       │  metadata.customer_id=<uuid>
                       ▼
                    customer-tier-bump Edge Function (NEW)
                       │
                       ├─ 1. Resolve customer_id → vps_instance row (host+port)
                       │
                       ├─ 2. UPDATE customers SET tier=<target_tier>
                       │
                       ├─ 3. POST provisioning service /tier-bump
                       │     (provisioning service holds the SSH key, not Supabase)
                       │     ─► provisioning service:
                       │          ssh weuseai@<host> "
                       │            sed -i 's/^WEUSEAI_TIER=.*/WEUSEAI_TIER=<target_tier>/' \\
                       │              /home/weuseai/.hermes/.env &&
                       │            sudo systemctl restart hermes-gateway
                       │          "
                       │     ─► Hermes boot triggers ExecStartPre=+/usr/local/bin/weuseai-bundle-pull
                       │     ─► bundle-pull script reads new WEUSEAI_TIER from .env
                       │     ─► tier filter installs/removes SKILL.md files per new tier
                       │     ─► customer keeps their bundle version pinned (no surprise update)
                       │
                       ├─ 4. INSERT INTO tier_change_events (customer_id, from_tier, to_tier, reason='xendit_invoice_paid', xendit_invoice_id, completed_at)
                       │
                       └─ 5. Send Telegram nudge to customer:
                              "Tier kamu udah Pro. Skill baru bakal aktif dalam ~30 detik. ✓"
```

**Why proxy via provisioning service rather than SSH from Edge Function directly:** the SSH private key for fleet access stays in Fly.io secrets (where the provisioning service already lives). Putting it in Supabase Edge Function secrets means anyone with read access to the Supabase project (founder + future ops hires + any service-role-leaking bug) gets fleet root. Recommendation #2 below.

### customer-flow.ts bundle delivery wiring

```
Customer onboarding (Phase 2B) picks persona via dashboard
       │
       ▼
customer-flow.ts spinUpAgent({ customerId, tier, agentSlug })
       │
       ├─ Read agent-packs/<agentSlug>/_bootstrap-bundle.tar.gz (~5KB) into memory
       │   ↑ already exists, built by scripts/build-bootstrap-bundle.ts at PR-time
       │
       ├─ buildSetupScript({
       │     ...,
       │     bundleTarBase64: <inline 5KB bootstrap, base64-encoded>,
       │     agentSlug,
       │     tier,
       │   })
       │
       └─ ssh.runSetup({ ... script ... })
              │
              ▼ (on VPS first boot)
              setup-script extracts bootstrap → installs ExecStartPre →
              Hermes start → bundle-pull pulls FULL bundle from Storage →
              tier filter applies → customer chats with full agent capabilities
```

**Inline bootstrap = SLA floor.** Customer can chat from second 1 even if Storage is dead. Full bundle is best-effort, retries on every boot. (This is the hybrid pattern locked in 2E-2 — Phase 2E-3 just wires the missing call site.)

### PDF rendering pipeline

```
Customer message: "bikin invoice 8 jam @800rb buat PT Acme"
       │
       ▼
Hermes (on VPS) matches invoice-generator skill, extracts params
       │
       ▼
POST workflow-execute Edge Function
       │
       ▼
invoice-generator-handler (existing)
       │
       ├─ Render Bahasa invoice template → HTML
       │
       ├─ POST <PDF_RENDERER_URL>  ◄── NEW: external dependency
       │     body: { html: <rendered>, options: { format: 'A4' } }
       │     ─► returns PDF bytes
       │
       ├─ Upload PDF to Storage (NEW bucket: pdf-renders)
       │     30-day TTL signed URL
       │
       └─ return { signed_url, expires_at, format: 'pdf' }
       │
       ▼
Hermes wraps with persona voice, replies via Telegram with the PDF URL
```

External dependency choice: see "Open question 1" below + sub-spec doc `docs/plans/2026-05-08-phase-2e-3-pdf-renderer-decision.md`.

### bundle_pull_attempts retention

```
Supabase Scheduled Function: nightly at 03:00 UTC
       │
       ├─ For each customer with attempts older than 30 days:
       │   ─ Aggregate into bundle_pull_attempts_summary:
       │     (customer_id, week_start, attempt_count,
       │      success_count, failure_count, avg_duration_ms)
       │   ─ DELETE the raw rows
       │
       └─ Retain raw rows for last 30 days (trailing window for debugging)
```

This keeps the table size bounded at `customers × 30 boots × 7 days ≈ <100k rows steady-state`. Aggregate table grows linearly in customer-weeks.

## External dependency: PDF renderer

Three options. Sub-spec doc: `docs/plans/2026-05-08-phase-2e-3-pdf-renderer-decision.md` (to draft alongside this).

| Option | Cost | Ops | Pros | Cons |
|---|---|---|---|---|
| **Browserless.io** (managed) | ~$0.001/render @ pay-as-you-go, $50/mo for 100k | Zero | Mature, good Bahasa font support, fast (< 2s), reliable | Recurring SaaS dependency, vendor lock-in (modest) |
| **Cloudflare Browser Rendering** (managed) | $5/mo for 100k requests | Zero | Cheaper, Cloudflare-adjacent (already using CF for landing/proxy), no custom Docker | Beta as of 2026-Q1 (verify GA status), Bahasa font handling untested |
| **WeasyPrint** (self-hosted) | $0 LLM/render but VPS cost | High — Python deps, font installation, font-fallback debugging | No vendor lock-in, free at scale | Operational burden (we maintain it), HTML/CSS rendering subset (no flexbox in older versions) |

**Recommendation: Cloudflare Browser Rendering.** Cheap, integrates with our existing Cloudflare Workers proxy stack, and the cost ceiling stays predictable. Browserless is the safe fallback if CF Browser Rendering has Bahasa font issues. WeasyPrint adds a service we have to babysit; defer until we hit a scale where SaaS cost matters (likely 1000+ paying customers).

**3 functions need the JWT-role pattern applied.** Each gets a corresponding test in `tests/<fn>-handler-auth.spec.ts` asserting:

4. `Bearer <anon JWT>` → 401.
5. `Bearer <malformed>` → 401.

### Q5 — PDF storage + email delivery: ✅ Separate `pdf-renders` bucket, 30-day TTL **+ email-on-render**
Plus expanded scope (founder follow-up): when invoice-generator renders the PDF, send an email to the customer with the PDF attachment (or signed URL — see implementation note below). Subject: `"Invoice <number> — <client_name>"`. From: `noreply@weuseai.agent` (configurable). Solves "customer needs invoice 2 months later when our 30-day signed URL has expired" — they have it permanently in their email.

Email infrastructure: **Resend** (recommendation). $0/mo for 3000 emails covers 2026 customer projection. Existing Supabase email if the founder has it set up takes precedence. Email body in Bahasa, "kamu" register, no banned words, no exclamation marks (per CLAUDE.md brand voice).

Implementation choice — attach PDF directly vs send signed URL:
- **PDF attachment** (recommendation): customer keeps the file forever; no dependency on our Storage retention. Resend supports up to 40MB attachments; an A4 invoice PDF is typically <100KB.
- Signed URL: customer can re-download but loses access at TTL.

Going with PDF attachment unless attachment size becomes a concern.

### Q6 — JWT-role audit scope: ✅ All 3 affected Edge Functions

**Audit reasoning (locked, for future contributors).** I scanned all 9 deployed Edge Functions for the `token === SERVICE_KEY` raw-equality pattern that broke on Supabase's new sb_secret_* key system. Three categories of "no action needed":

| Category | Functions | Why no action |
|---|---|---|
| Webhook signature auth (not bearer) | `xendit-webhook` | Validates via Xendit's `x-callback-token` header signature, not bearer JWT. Different threat model; signature stays valid. |
| Customer-id + active-subscription gate (not service auth) | `workflow-list`, `workflow-execute`, `bundle-fetch`, `bundle-pull-record` | Customer functions; the auth check is "is this customer_id valid + does their subscription cover this skill" — bearer role doesn't enter the picture. |
| Already correct (post-2E-2) | `bundle-publish` | Fixed during 2E-2 — JWT-role pattern in place. |

Three functions DO need the pattern applied in 2E-3:

| Function | Current auth | After fix |
|---|---|---|
| `create-invoice` (2A) | service-role bearer raw equality | JWT-role decode + `role === 'service_role'` |
| `invoice-generator-handler` (2E-1) | service-role bearer raw equality | Same |
| `daily-briefing-handler` (2E-1) | service-role bearer raw equality | Same |

Each gets the canonical decoder from `bundle-publish` lifted into a shared helper at `supabase/functions/_shared/admin-auth.ts` (one source of truth) + 5 regression tests per function.

Plus a one-page reference doc at `docs/security/jwt-role-pattern.md` (founder follow-up) so Phase 2E-3+ Edge Functions don't re-derive the pattern from scratch.
