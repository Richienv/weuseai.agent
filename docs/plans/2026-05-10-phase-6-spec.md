> **Status:** DRAFT 2026-05-10 — pending founder review. Builds on Phase 5 LOCKED 2026-05-09 (Q1-Q5: A, A, A, C, C). No implementation until Q-list locked.

## Why this exists

Phase 5 ships **BD v3 + 5 department dispatch packs + approval queue + cross-session memory**. Studio-tier customers get a Master Agent that walks them from "idea" to "10 paying customers" with proper Indonesian-context scaffolding.

But Phase 5 is still a **scoped concierge** — every irreversible action surfaces an approval gate, every department dispatch is a one-shot facade routing to a specialist, and no work happens autonomously between customer messages.

Phase 6 = **full Cofounder-Clone**. The customer wakes up Monday morning to a digest: "While you were asleep, sales-team contacted 12 leads via the email sequence we agreed on Friday, marketing-team published the IG carousel + 3 Stories per the Q3 calendar, eng-team merged 2 PRs from the kanban backlog. Here's what needs your input today: 1 contract draft, 2 pricing decisions, 1 vendor selection."

This is the founder's **"stuck-at-airport-Wi-Fi-and-business-runs-without-me"** vision per `phase_5_cofounder_ambition.md` (memory file). Phase 5 made the cofounder _exist_; Phase 6 makes the cofounder _operate_.

                 ────────────────                    ────────────────────

  Customer ──→ BD v3 ──→ approval gate ──→ specialist     Customer ──→ BD v3
              (per-message conversation)                              │

                                                                      │   ├─ rep-1 (lead-gen)
                                                                      │   ├─ rep-2 (outreach)
                                                                      │   └─ rep-3 (close)

                                                                      │   └─ video-editor
                                                                      ├─ Engineering workspace
                                                                      │   ├─ pm
                                                                      │   ├─ backend-eng
                                                                      │   └─ frontend-eng
                                                                      ├─ Legal workspace (lighter)
                                                                      └─ Finance workspace (lighter)
                                                                              │
                                                                              ▼
                                                                      Pre-approved action

The big shifts:
1. **Department workspaces** persist (stateful "team rooms" with simulated personas).
2. **Pre-approved action patterns** — customer locks a pattern once ("approve all IG posts that match brand voice + don't claim health benefits"); future matching actions auto-execute.
3. **Multi-week autonomous execution** — BD v3 runs 24/7, sends Monday digests, surfaces only what needs decisions.
4. **Custom codebase integration** — eng workspace clones customer's GitHub repo, opens PRs, runs tests.

## Locked scope (TBD — pending founder review)

**Suggested IN Phase 6:**

1. **Department workspaces** — 5 persistent "team rooms" (Sales / Marketing / Eng / Legal / Finance). Each has 2-4 simulated personas with names, areas of focus, and persistent task queues. Surface as Telegram threads per dept (one chat per team).
2. **Pattern-based pre-approval** — `approval_patterns` table stores customer-locked patterns ("auto-approve action X when matches Y conditions"). Approval queue checks patterns first; only novel actions surface.
3. **Daily digest engine** — cron-driven Monday/Wednesday/Friday morning digest summarizing what departments did + what needs decisions.
4. **Codebase integration (eng workspace only)** — connect customer's GitHub repo, open PRs from kanban tasks, run customer-supplied test commands.
5. **Long-running task orchestration** — kanban tasks with multi-day SLAs that BD v3 monitors + escalates.

**Suggested DEFERRED to Phase 7+:**

- Multi-tenant cofounder-vs-cofounder (e.g. founder + CTO both have agent twins).
- Voice-call interface (currently text-only via Telegram).
- Auto-generated investor updates (founder-trigger only in Phase 6).
- Capital allocation suggestions (Trade Pro extends, but tier above current scope).

## Architecture

### Schema migrations needed (~5 new tables + extensions)

```sql
-- 20260601000000_phase_6_cofounder_clone.sql

-- 1. Department workspaces — persistent state per dept per customer
CREATE TABLE IF NOT EXISTS public.department_workspaces (
  id              uuid primary key default gen_random_uuid(),
  customer_id     uuid not null references public.customers(id) on delete cascade,
  department      text not null check (department in (
    'sales', 'marketing', 'engineering', 'legal', 'finance'
  )),
  -- Configured at workspace setup time, immutable thereafter
  simulated_team  jsonb not null default '[]'::jsonb,
  -- Free-form workspace meta (charter, OKRs, current focus areas)
  charter_md      text,
  -- Single Telegram thread per workspace for ongoing chat
  telegram_thread_id text,
  status          text not null check (status in (
    'active', 'paused', 'archived'
  )) default 'active',
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now(),
  unique (customer_id, department)
);

-- 2. Approval patterns — customer-locked auto-approval rules
CREATE TABLE IF NOT EXISTS public.approval_patterns (
  id              uuid primary key default gen_random_uuid(),
  customer_id     uuid not null references public.customers(id) on delete cascade,
  -- Which action_kind this pattern matches (matches Phase 5-1.a enum)
  action_kind     text not null,
  -- JSON-shape match conditions. Example for public_emission:
  --   { "channel": "ig", "must_pass_brand_voice": true,
  --     "max_audience": 10000, "no_health_claims": true }
  match_conditions jsonb not null,
  -- Customer's reasoning (for audit + edit later)
  reasoning_md    text,
  status          text not null check (status in (
    'active', 'suspended', 'revoked'
  )) default 'active',
  created_at      timestamptz not null default now(),
  -- When this pattern was last triggered (for analytics)
  last_matched_at timestamptz,
  match_count     integer not null default 0
);

-- 3. Daily digests — what BD v3 surfaces M/W/F morning
CREATE TABLE IF NOT EXISTS public.daily_digests (
  id              uuid primary key default gen_random_uuid(),
  customer_id     uuid not null references public.customers(id) on delete cascade,
  digest_date     date not null,
  -- Compact summary by department (rendered to Telegram + dashboard)
  body_md         text not null,
  -- Action items requiring customer decision (links to approval_requests)
  pending_decisions jsonb not null default '[]'::jsonb,
  delivered_at    timestamptz,
  read_at         timestamptz,
  created_at      timestamptz not null default now(),
  unique (customer_id, digest_date)
);

-- 4. Codebase integrations — per-customer GitHub repo connections
CREATE TABLE IF NOT EXISTS public.codebase_integrations (
  id              uuid primary key default gen_random_uuid(),
  customer_id     uuid not null references public.customers(id) on delete cascade,
  github_repo     text not null,                       -- "owner/repo"
  -- Encrypted GitHub fine-grained PAT (read+PR scope only)
  github_pat_encrypted text not null,
  -- Customer-supplied build/test commands (run inside sandboxed VPS)
  test_command    text,
  build_command   text,
  status          text not null check (status in (
    'active', 'suspended', 'revoked'
  )) default 'active',
  created_at      timestamptz not null default now(),
  unique (customer_id, github_repo)
);

-- 5. Persona memories — long-running per-team-member context
-- (Each simulated persona accumulates context across sessions)
CREATE TABLE IF NOT EXISTS public.persona_memories (
  id              uuid primary key default gen_random_uuid(),
  workspace_id    uuid not null references public.department_workspaces(id) on delete cascade,
  persona_slug    text not null,                       -- e.g. 'sales-rep-1'
  memory_kind     text not null check (memory_kind in (
    'lead', 'contact', 'project', 'commitment', 'preference', 'recall'
  )),
  body_md         text not null,
  source          text,                                -- which task/conversation surfaced this
  created_at      timestamptz not null default now()
);

CREATE INDEX IF NOT EXISTS idx_persona_memories_workspace
  ON public.persona_memories (workspace_id, persona_slug, created_at DESC);

-- RLS — same convention as Phase 5
ALTER TABLE public.department_workspaces ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.approval_patterns ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.daily_digests ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.codebase_integrations ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.persona_memories ENABLE ROW LEVEL SECURITY;

CREATE POLICY "anon read own workspaces"
  ON public.department_workspaces FOR SELECT TO anon USING (true);
CREATE POLICY "anon read own approval_patterns"
  ON public.approval_patterns FOR SELECT TO anon USING (true);
CREATE POLICY "anon read own digests"
  ON public.daily_digests FOR SELECT TO anon USING (true);
-- codebase_integrations + persona_memories: service-role only (no anon read)

-- Extension to customers — enable phase_6_enabled gate
ALTER TABLE public.customers
  ADD COLUMN IF NOT EXISTS phase_6_enabled boolean not null default false;
```

### Edge Functions specified (~6 new)

| Function | Purpose | Auth |
|---|---|---|
| `workspace-setup-handler` | Create + configure dept workspace per customer (one-time per dept). | HMAC (Phase 5-3.c) |
| `pattern-match-handler` | Check incoming approval request against active patterns; auto-approve if match. Called inline from approval-queue create. | service-role internal |
| `daily-digest-builder` | Cron-triggered M/W/F. Aggregates dept activity + pending decisions; writes daily_digests row + sends to Telegram. | cron + service-role |
| `codebase-pr-opener` | Eng workspace task → GitHub PR open via PAT. | HMAC + per-customer PAT decrypt |
| `digest-read-marker` | Customer opens digest → mark read_at. | HMAC |
| `pattern-edit-handler` | Customer reviews + edits/revokes patterns via dashboard. | dashboard auth (Phase 6) |

### Pattern-matching engine (the crux of Phase 6)

The `match_conditions` jsonb is a **declarative rule set** evaluated against approval payloads. Examples:

```json
// Marketing dept: auto-approve IG posts that pass brand voice
{
  "channel": "ig",
  "must_pass_brand_voice": true,
  "no_health_claims": true,
  "no_financial_claims": true,
  "audience_max": 10000
}

// Sales dept: auto-approve cold-email batches matching template family
{
  "template_family": "outbound-saas-2026",
  "batch_size_max": 50,
  "personalization_fields_required": ["name", "company"]
}

// Eng dept: auto-merge dependabot bumps that pass tests
{
  "pr_kind": "dependabot",
  "tests_must_pass": true,
  "max_files_changed": 1,
  "no_breaking_changes_label": true
}
```

The pattern-matcher is a pure function:

```typescript
// supabase/functions/_shared/pattern-matcher.ts (Phase 6-1)
matchPattern(action_payload, pattern_conditions): boolean
```

Tests: ~30 cases covering `must_pass_brand_voice` (delegates to existing transform-llm-output Phase 4-4), `tests_must_pass` (delegates to codebase-pr-opener test-command result), and primitive equality / range / list-membership conditions.

## State machine extension

Phase 6 adds two new transitions to the approval lifecycle:

```
                    ┌─ matches active pattern → auto_approved → execute
   pending ──────── ┤
                    └─ no match → pending → customer reviews → approved/rejected
```

`approval_requests` schema gets a new optional `auto_approved_by_pattern_id` column referencing `approval_patterns.id`. Status flips from `pending` to `approved` immediately on match, with `approved_by = "pattern:<id>"`.

Each workspace has 2-4 simulated team members. Configuration locked at workspace setup time. Example for Sales:

```json

  "team": [
    {
      "slug": "sales-rep-1",
      "name": "Andin",
      "role": "Lead generation specialist",
      "voice_anchor": "Friendly outbound; warm openers; respects no",

    {
      "slug": "sales-rep-2",
      "name": "Bayu",
      "role": "Closing specialist",
      "voice_anchor": "Calm, decision-oriented, prefers async",
      "skills_used": ["proposal-builder", "objection-handling"]
    },
    {
      "slug": "sales-mgr",
      "name": "Citra",
      "role": "Pipeline manager + reporting",
      "voice_anchor": "Direct, numbers-first",
      "skills_used": ["pipeline-aggregation", "forecast-building"]

```

These aren't separate Hermes instances — they're persona modes inside a single Hermes session per workspace. Voice anchors enforce consistency. Skills used pin the routing.

## Open questions (for founder review before LOCK)

These are blocking → spec stays DRAFT until founder picks. **Six questions:**

### Q1: Auto-approval pattern UX — pre-config or learn-from-customer-behavior?
- **A. Customer pre-configures patterns explicitly** via dashboard ("approve all IG posts matching X"). Most explicit; lowest auto-approval rate week-1.
- **B. BD v3 learns from past approve/reject decisions** + suggests patterns ("I noticed you approved 5 similar IG posts; want me to auto-approve future ones?"). Highest auto-approval rate; needs explainability gate.
- **C. Hybrid:** start with A; add B-style suggestions after 30 days.

**Recommendation:** C. A is simpler ship; B without history risks runaway auto-approve. Suggestion-based learn after 30 days bridges both.

### Q2: Department workspace persona naming — Indonesian names or generic?
- **A. Indonesian names** (Andin, Bayu, Citra) — cultural fit, customer feels they have an actual team.
- **B. Generic role labels** ("Sales Rep 1", "Closing Specialist") — clearer this is AI; less anthropomorphism risk.
- **C. Customer chooses** at workspace setup time.

**Recommendation:** C. Default to A (Indonesian names) but let customer override. Anthropomorphism is a feature for solo founders feeling alone.

### Q3: Daily digest cadence — fixed M/W/F or customer-configurable?
- **A. Fixed M/W/F morning** (07:00 WIB). Predictable.
- **B. Customer-configurable** (daily / 2x/week / weekly).
- **C. Adaptive** based on activity volume (high activity → daily; low → weekly).

**Recommendation:** A initially. Most customers won't tune it. Phase 7+ can add B if signal.

### Q4: Codebase integration — opt-in by default, or default-on for Studio?
- **A. Opt-in always** (privacy-respecting; customer explicitly connects GitHub).
- **B. Default-on at Studio tier** (assumes they want eng workspace to operate).
- **C. Opt-in at sign-up; reminded weekly** until enabled.

**Recommendation:** A. GitHub PAT is sensitive; force conscious opt-in. Studio customers expect this UX.

### Q5: Multi-week autonomous execution — bounded or unbounded?
- **A. Unbounded** — kanban tasks run as long as needed; BD v3 surfaces only at decision points.
- **B. 7-day max per task** — anything longer must be re-confirmed by customer.
- **C. Per-action-kind bounded** (similar to Q4=C in Phase 5: incorporate=14d, public_emission=24h).

**Recommendation:** B. 7 days is a natural Indonesian-business-week cadence. Forces customer engagement without micromanaging. If real signal for longer, extend in Phase 7.

### Q6: Cost ceiling — per-customer monthly LLM token budget?
- **A. Hard cap per customer** (e.g. $50/month LLM tokens; pause if exceeded).
- **B. Soft cap with surge billing** (warn at 80%, charge customer for overage).
- **C. No cap** (trust customers; deal with abuse case-by-case).

**Recommendation:** A initially. Studio is paying Rp 4.9jt setup; LLM at $50/month = ~Rp 800k/month. Cap protects margins; raise to $100/month if customer hits frequently and asks.
